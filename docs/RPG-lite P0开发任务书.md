## 一、阶段目标

P0 不是完整 RPG，也不是重做整个游戏。P0 只验证一个核心问题：

> 孩子是否能理解自己在星光小镇中扮演“星路修复员”，接到委托，进入场景，完成英语挑战，获得奖励，并看到小镇变化。

本阶段完成后，玩家应该能自然说出：

- 我是星路修复员。
- 我要修复故事钟塔第一圈星路。
- 我需要完成 3 个委托，找回 3 个星片。
- 每完成一个委托，我会获得奖励。
- 完成 3 个委托后，第一圈星路会点亮。

## 二、P0 范围

### 必须做

- 主城只展示当前主线委托。
- 冒险日志清楚说明当前目标、下一步、奖励。
- 3 个试玩任务完整 RPG 化：
  - `小镇门口见面礼`
  - `帮 Mina 赶上铃声`
  - `天气出门准备`
- 完成任务后展示奖励结算。
- 增加最小经验和等级反馈。
- 完成 3 个任务后出现章节完成反馈。
- 场景画面保持干净，不出现明显遮挡和调试感元素。

### 明确不做

- 不做战斗系统。
- 不做自由地图移动。
- 不做完整背包。
- 不做完整图鉴。
- 不做完整徽章系统。
- 不做区域锁定系统。
- 不扩展到 75 个任务。
- 不引入 AI 生成内容。
- 不重写 `TaskRuntime`。

## 三、核心玩法闭环

P0 必须跑通以下流程：

1. 玩家进入星光小镇。
2. 主城显示当前主线目标：修复钟塔第一圈星路。
3. 玩家看到当前委托和奖励预览。
4. 玩家点击开始，进入对应场景。
5. 右侧冒险日志告诉玩家当前要做什么。
6. 玩家在冒险日志中完成英语挑战。
7. 系统弹出奖励结算。
8. 玩家获得经验、星星和星片。
9. 主城或章节进度发生变化。
10. 玩家继续下一个委托。
11. 完成 3 个委托后，显示“第一圈星路点亮”。

## 四、组织分工

### 项目经理 / 游戏策划

负责人：项目经理 / 游戏策划负责人

职责：

- 冻结 P0 范围。
- 输出主线故事和 3 个委托包装。
- 明确奖励命名和奖励用途。
- 维护验收标准。
- 控制需求变更，不让 P0 膨胀。
- 每轮按截图和完整流程验收。

交付物：

- P0 开发任务书。
- 3 个委托的故事包装。
- 奖励结算文案。
- 试玩验收清单。

### 架构组

职责：

- 判断现有代码如何承接 RPG-lite P0。
- 设计最小成长数据结构。
- 约束模块边界，避免大重构。
- 确认旧存档兼容方案。
- 判断哪些内容放在 React，哪些留在 Phaser。

交付物：

- P0 技术实现方案。
- 数据结构变更说明。
- 风险点和影响范围说明。

架构原则：

- 不重写任务判定系统。
- 不引入复杂状态管理库。
- 不引入后端。
- 不引入 AI 服务。
- 不为 P1 系统提前过度设计。

### 代码组

职责：

- 实现成长字段：等级、经验、称号。
- 改造顶部状态栏。
- 改造任务面板为冒险日志。
- 改造任务完成弹窗为奖励结算。
- 接入任务完成后的经验结算。
- 确保 3 个任务完整可玩。
- 确保桌面和手机视口基本可用。

交付物：

- 可运行 P0 版本。
- 内容校验通过。
- 构建通过。
- 桌面和手机截图。

实现原则：

- 按任务单实现，不自由追加功能。
- 优先稳定和清楚，不追求系统完整。
- 画布中不放大段说明文字。
- 任务操作统一放在冒险日志中。

### 美术组

职责：

- 定义主城当前委托面板视觉。
- 定义冒险日志视觉。
- 定义奖励结算弹窗视觉。
- 检查角色比例和场景遮挡。
- 检查画布内是否出现调试标签、浮空按钮、半截文字。

交付物：

- 主城 P0 视觉稿或截图标注。
- 冒险日志视觉规范。
- 奖励结算视觉规范。
- 场景截图验收意见。

美术原则：

- 画面先干净，再可爱。
- UI 不能压住关键美术元素。
- 按钮必须属于明确容器。
- 文案不能挤出框。
- 角色不能变形。

### QA / 试玩

职责：

- 按完整流程试玩 3 个委托。
- 检查每一步是否知道下一步做什么。
- 检查奖励是否清楚。
- 检查截图中的视觉 bug。
- 记录儿童试玩观察点。

交付物：

- P0 试玩记录。
- 桌面截图验收。
- 手机截图验收。
- 问题清单和优先级。

## 五、P0 产品任务

### 1. 主城改造

目标：

- 星光小镇成为 RPG-lite 冒险起点。
- 玩家进入后立刻知道当前主线目标和当前委托。

要求：

- 主城只展示一个当前委托。
- 当前委托包含标题、故事原因、奖励预览、开始按钮。
- 开始按钮必须在委托面板中。
- 不展示多个半透明叠层卡片。
- 不出现半截 toast。

验收：

- 进入主城 10 秒内能看懂下一步。
- 截图中无明显遮挡、重叠、漂浮按钮。

### 2. 冒险日志改造

目标：

- 原任务面板升级为“冒险日志”。
- 冒险日志成为玩家理解目标和操作的唯一主信息区。

要求：

- 展示当前主线：钟塔第一圈星路。
- 展示当前委托。
- 展示故事原因。
- 展示当前步骤目标。
- 展示奖励预览。
- 展示下一步按钮。

验收：

- 玩家不需要猜点击哪里。
- 每一步都能从冒险日志看懂操作。
- 任务场景不依赖画布内大段文字说明。

### 3. 奖励结算改造

目标：

- 完成任务后让玩家清楚知道获得了什么，以及这个奖励修复了哪里。

要求：

- 展示经验。
- 展示星星。
- 展示星片或装饰奖励。
- 展示知识成长。
- 展示小镇变化。
- 提供继续下一委托或回主城按钮。

验收：

- 每个任务完成后都有明确奖励。
- 奖励不是抽象数字，必须有故事用途。

### 4. 成长系统最小实现

目标：

- 给 RPG-lite 提供最小成长反馈，不做复杂数值系统。

要求：

- 新增等级。
- 新增经验。
- 新增称号。
- 每个委托发放固定经验。
- 经验满后可以升级。
- 顶部状态栏能展示等级和经验。

验收：

- 完成任务后经验增加。
- 达到阈值后等级增加。
- 旧存档不报错。

### 5. 3 个委托 RPG 化

任务一：小镇门口见面礼

- 故事原因：新朋友还不知道怎么打招呼，问候星片掉进邮局书房。
- 学习目标：问候与身份确认。
- 奖励：问候星片。
- 修复结果：小镇门口恢复欢迎光。

任务二：帮 Mina 赶上铃声

- 故事原因：钟塔作息铃慢了一拍，Mina 可能错过提醒。
- 学习目标：时间表达和日常顺序。
- 奖励：小闹钟装饰。
- 修复结果：钟塔作息铃重新响起。

任务三：天气出门准备

- 故事原因：欢迎会要开始，但天气台没有亮。
- 学习目标：天气表达和出门准备。
- 奖励：天气贴纸。
- 修复结果：第一圈星路点亮。

验收：

- 三个委托能连续完成。
- 每个委托有故事原因、学习目标、奖励、修复结果。
- 完成第三个委托后出现章节完成反馈。

## 六、视觉验收标准

以下问题一律视为 bug：

- 人物变形。
- 文字超出容器。
- 文字压住关键美术。
- 半截 toast 或半截标签。
- 按钮漂浮在画面上。
- 多个 UI 卡片互相重叠。
- 场景里出现调试标签。
- 道具悬浮在不合理位置。
- 点击区域和视觉目标明显不一致。

每次版本验收必须提供：

- 主城桌面截图。
- 任务场景桌面截图。
- 冒险日志截图。
- 奖励结算截图。
- 手机视口截图。

## 七、技术验收标准

代码组交付前必须完成：

- `npm run verify`
- `npm run build`
- 桌面浏览器试玩。
- 手机视口试玩。
- 旧存档兼容测试。

如果当前环境没有 `npm`，至少必须完成：

- `node scripts/verify-content.mjs`
- 关键 JS 文件语法检查。
- 本地浏览器完整试玩。

## 十、最终交付定义

P0 完成不是指“代码写完”，而是指：

- 玩家可以从主城开始冒险。
- 玩家可以完成 3 个委托。
- 玩家能看懂目标、操作和奖励。
- 主城和场景截图无明显视觉 bug。
- 任务完成后有 RPG-lite 奖励结算。
- 第一圈星路完成后有章节反馈。
- 家长能理解孩子练习了哪些英语能力。
